## 1. Product Promise

Affinity Academy exists to develop independent designers, not merely users who can repeat software instructions.

A graduate must be able to:
1. identify and explain the relevant tools and features in the declared Affinity product scope;
2. choose an appropriate tool and workflow for a stated visual or production problem;
3. apply foundational design principles intentionally;
4. turn a brief into a coherent visual solution;
5. evaluate, revise, and explain their own design decisions; and
6. deliver an editable source file and fit-for-purpose exports.

Completing lessons, watching demonstrations, or passing recall quizzes alone is not evidence of graduation-level competence.

## 3. Learning Domains and Track Outcomes

Track names describe learning domains. They must not imply that the current product is necessarily three separately installed applications.

| Learning domain | Required learner capability |
|---|---|
| Designer / vector design | Construct and edit vector geometry; manage nodes, shapes, layers, symbols and type; create consistent visual systems; prepare reliable vector and print/web output. |
| Photo / raster and image editing | Select and mask accurately; edit and retouch with controlled, preferably non-destructive workflows; combine imagery; make coherent tonal/color decisions; export appropriately. |
| Publisher / editorial and layout design | Build clear page and publication structures; manage text flow, grids, typographic hierarchy, placed assets and preflight/output in the current Affinity Layout workflow. |
| Scripting / automation | Understand verified scripting and MCP capabilities, automate repeatable operations, handle errors, and inspect rendered results. This domain does not replace the manual design outcomes above. |

**Product-scope rule:** Current-product teaching must use the current Affinity application and its documented Layout, Vector, and Pixel studios. Affinity V2 StudioLink can appear only in a clearly labelled historical/legacy comparison. Do not teach StudioLink as the architecture of the current application.

## 4. Design Thinking Method

Substantial exercises and capstones must teach and assess this repeatable process:

1. **Discover:** Parse the brief; identify audience, purpose, message, constraints, references, and required deliverables.
2. **Define:** State the communication problem and measurable success criteria.
3. **Explore:** Generate more than one viable direction; compare hierarchy, layout, type, color, imagery, and tone.
4. **Plan:** Choose a visual system, document setup, grid, assets, and production workflow before detailed execution.
5. **Create:** Use appropriate Affinity tools and maintain a controllable, organized source document.
6. **Evaluate:** Check legibility, hierarchy, alignment, consistency, technical correctness, and fit to the brief.
7. **Iterate:** Explain what changed and why; use critique to improve the result rather than decorate it arbitrarily.
8. **Deliver:** Package the editable source and correctly configured exports; perform a final quality check.

Tutorials may guide early practice, but independent challenges must change the brief, assets, constraints, or intended audience so the learner cannot pass by copying the demonstration.

## 5. Competency Scale

Use this scale for tool and design outcomes. It measures learner performance, not the inventory status of a tool.

| Level | Label | Evidence |
|---|---|---|
| 1 | Recognize and explain | Correctly identifies the tool/principle and explains its purpose and main limitation. |
| 2 | Guided execution | Completes a known task with instructions, hints, or a worked example. |
| 3 | Independent execution | Chooses and uses the right method without step-by-step prompts; produces a correct result. |
| 4 | Transfer and diagnose | Adapts the method to a novel constraint, diagnoses problems, compares alternatives, and justifies trade-offs. |

A learner must not be labelled proficient based only on Level 1 or Level 2 evidence.

## 6. Minimum Teaching Contract for Every Lesson

The existing lesson schema's ten standard sections remain the structural baseline. Authors must apply the following instructional contract without silently weakening schema validation:

| Existing schema section | Required instructional evidence |
|---|---|
| `learningObjectives` | Measurable outcomes using an observable verb and a success condition. |
| `foundationalKnowledge` | The concept and prerequisite mental model, including why the operation matters. |
| `toolAndFeatureExplanation` | Exact current product area, tool/feature name, purpose, important options, shortcut/modifiers when verified, and limitations. |
| `stepByStepInstructions` | Reproducible guided workflow with decision points, not clicks without explanation. |
| `visualExamples` | Visual evidence of correct/incorrect choices, before/after, or meaningful alternatives. |
| `guidedPractice` | A constrained exercise that allows coached repetition. |
| `independentChallenge` | A changed task requiring learner choice and transfer, not a copy of the demonstration. |
| `commonPitfalls` | Likely errors, how to recognize them, and safe recovery. |
| `knowledgeCheck` | At least one conceptual "why/when" check as well as relevant factual or procedural checks. |
| `summaryAndResources` | Key principles, verified references, and a prompt for reflection or next-step application. |

A lesson may introduce one or several tools, but all referenced tools must resolve to entries in the Tool Coverage Matrix once that matrix is populated. Do not invent shortcuts, contextual options, or version-specific behaviour.

## 7. Assessment and Graduation

Assessment is cumulative; attendance and lesson completion are progress indicators, not proof of mastery.

- **Lesson:** Check concept understanding and observable execution.
- **Module:** Require a practical task that combines the module's core tools and concepts.
- **Track:** Require a self-directed project appropriate to the discipline.
- **Programme:** Require an integrated portfolio/capstone based on a new brief, with planning, alternatives, final work, editable source, exports, and a short design rationale.

### Common capstone rubric

Score each dimension from 1 to 4 using the competency scale above.

| Dimension | What is assessed |
|---|---|
| Brief and audience | The solution addresses the actual communication goal and constraints. |
| Design reasoning | Hierarchy, composition, typography, color, imagery, and spacing are purposeful and coherent. |
| Tool and workflow choice | Tools and workflow suit the task; the learner can explain alternatives and trade-offs. |
| Craft and consistency | Alignment, detail, organization, editability, and finish meet the brief. |
| Iteration and critique | The learner identifies issues and makes meaningful evidence-based improvements. |
| Delivery | Source and exports are complete, correctly named, and appropriate to the requested medium. |
| Reflection | The learner can explain decisions, limitations, and what they would improve next. |

**Proposed graduation threshold:** every critical rubric dimension must score at least Level 3 (Independent execution). A high average cannot compensate for a critical failure such as an unreadable deliverable, a broken source file, or a result that does not meet the brief. QA must approve the rubric and capstone briefs before this threshold is used for certification.

## 8. Completion and Claims Control

The programme may claim comprehensive tool coverage only after the version-scoped inventory has been independently checked against the current application and authoritative references.

The programme may claim design competence only after independent assessment evidence exists. Do not convert a planned lesson, a tool encyclopedia entry, a successful tutorial reproduction, or a passing software test into a learner outcome claim.

This document defines the approved direction and acceptance model. It does **not** claim that the tool inventory, all lesson mappings, capstones, or graduation assessments have already been implemented.
